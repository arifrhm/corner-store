# C-08 Volume Limit — 요구사항 명세서

> **저술 지위 고지.** 본 부품은 ADR-008(D-B)이 신규 도입한 부품으로서 대응하는 element walkthrough가 존재하지 아니한다. 따라서 **제1부의 법적 논증은 파생이 아니라 본 명세에서 1차 저술한 것**이며, 확정에 앞서 법률 검토를 요한다(제4절). 또한 본 부품은 Element Pool Freeze v1(ADR-004)에 포함되지 아니하였으므로, 채택에 앞서 부품 목록에의 신규 등재 절차를 요한다.

본 문서는 컴플라이언스 부품 C-08(물량 한도)의 요구사항 명세서이다. **제1부**는 본 부품이 강제하는 규율의 법적 근거와 그 도출 과정을, **제2부**는 이를 구현하기 위한 인터페이스·상태·인수 기준을 규정한다. 시스템 공유 개념은 `SPEC.md`에 의한다.

# 제1부. 법적 근거 및 논증

## 1. 개요

C-08은 발행인의 계열자(affiliate)가 Rule 144에 따라 제한증권 또는 지배증권을 재매각할 때, 일정 기간 동안 매도할 수 있는 수량이 관계 규정이 정한 한도를 초과하지 아니하도록 이를 산정·통제하는 부품이다. 계열자는 발행인을 지배하거나 발행인에 의하여 지배되는 지위에 있어 다량의 물량을 시장에 유입시킬 능력이 있으므로, Rule 144는 계열자의 재매각 수량에 상한을 두어 그 재매각이 사실상 배포에 이르지 아니하도록 한다. 본 부품은 그 수량 상한의 준수 여부를 판정한다.

## 2. 물량 한도의 규범적 근거

증권법 §4(a)(1)의 거래 면제는 발행인·인수인·딜러가 아닌 자의 거래에 한하여 적용되며(15 U.S.C. § 77d(a)(1)), 배포에 참여하는 자는 §2(a)(11)의 인수인에 해당할 수 있다(15 U.S.C. § 77b(a)(11)). 계열자는 그 지위상 다량의 증권을 점진적으로 시장에 방출(dribble-out)함으로써 실질적으로 배포를 수행할 위험이 있다. Rule 144(e)는 이러한 위험에 대응하여 계열자가 일정 기간에 매도할 수 있는 수량을 제한함으로써, 재매각이 배포가 아닌 통상의 거래에 머무르도록 한다(17 C.F.R. § 230.144(e)). 물량 한도는 곧 "한 번에 얼마만큼이 시장에 유입될 수 있는가"를 통제하는 장치이다.

## 3. 쟁점별 논증

### 3.1 적용 대상: 계열자에 한한 조건부 요건

물량 한도가 모든 매도인에게 적용되는지가 문제된다. Rule 144(e)의 물량 한도는 계열자(및 계열자와 합산되는 자)의 매도에 적용되며, 보유기간을 충족한 비계열자의 매도에는 원칙적으로 적용되지 아니한다. 따라서 본 부품은 매도인이 계열자로 판정된 경우에 한하여 활성화되는 조건부 요건이다. 매도인의 계열자 여부는 부품 A-06(affiliate)이 판정하며, 본 부품은 그 판정 결과를 전제로 작동한다.

### 3.2 한도의 산정: 두 기준 중 큰 값

한도를 어떻게 산정하는지가 문제된다. Rule 144(e)(1)은 3개월의 기간 동안 매도할 수 있는 수량을 두 기준 중 큰 값으로 정한다. 첫째는 해당 종류 증권 발행총량의 1%이고, 둘째는 매도 통지(Form 144) 제출 직전 4주간의 평균 주간 보고 거래량이다. 이는 유동성이 큰 증권일수록 시장에 흡수될 수 있는 물량이 크다는 점을 반영하여, 발행총량 기준과 실제 거래량 기준 중 매도인에게 유리한 큰 값을 상한으로 삼는 구조이다.

### 3.3 공개시장 부재 자산에서의 귀결

대상 자산과 같이 국가 거래소에 상장되거나 공표 시세가 형성되지 아니한 증권에서 위 두 기준이 어떻게 적용되는지가 문제된다. 4주 평균 주간 거래량 기준은 거래소 또는 공표 시스템에 보고되는 거래량을 전제로 하므로, 공개 거래시장이 존재하지 아니하는 증권에서는 그 값이 존재하지 아니하거나 영에 수렴한다. 그 결과 두 기준 중 큰 값은 발행총량의 1% 기준으로 귀착된다.

따라서 대상 자산의 맥락에서 실효적 상한은 발행총량의 1%이다. 이 귀결은 ADR-008(§2 D-B)이 확인한 바와 같으며, 거래량 기준의 부재가 곧 한도의 부재를 의미하지 아니한다는 점에 유의하여야 한다.

### 3.4 산정 기간과 누적 대상

한도의 준수를 어느 기간에 걸쳐 판단하는지가 문제된다. Rule 144(e)는 물량을 3개월의 기간을 단위로 산정하므로, 본 부품은 거래 시점을 기준으로 직전 3개월의 이동창(rolling window) 안에서 이미 체결된 매도 수량을 누적하고, 여기에 이번 거래의 수량을 더한 값이 상한을 초과하는지를 판정한다. 누적의 대상은 체결된 매도에 한하며, 거절되어 체결되지 아니한 시도는 포함하지 아니한다. 이동창의 성질상 3개월이 경과한 과거의 매도는 누적에서 제외된다.

### 3.5 합산 단위

물량을 누구의 매도까지 합산하여 산정하는지가 문제된다. Rule 144(a)(2) 및 (e)(3)은 매도 수량의 산정에 있어 매도인 본인의 매도뿐 아니라 그와 일정한 관계에 있는 자, 즉 동거 친족과 이들이 합산하여 일정 지분 이상을 보유하는 신탁·법인 등의 매도를 합산하도록 한다(17 C.F.R. § 230.144(a)(2), (e)(3)). 이는 계열자가 관련자를 통하여 한도를 잠탈하는 것을 방지하기 위함이다.

따라서 본 부품의 누적 상태는 지갑이나 개인이 아니라 이러한 합산 단위(person-group)를 키로 하여 관리되어야 한다. 합산 단위의 식별은 부품 A-06(control) 및 A-04(신원)에 의하며, 본 부품은 그 단위를 기준으로 매도 수량을 누적한다. 다만 §12(g)의 명의 보유자 산정(부품 D-01)과 본 부품의 (a)(2) 합산이 동일한 단위인지에 관하여는 별도의 확인을 요한다(제4절).

### 3.6 한도의 경계

상한값에 도달한 매도가 위반인지가 문제된다. Rule 144(e)의 문언은 수량이 상한을 초과(exceed)하지 아니할 것을 요구하므로, 상한에 정확히 도달한 매도는 적법하고 이를 초과하는 매도만이 위반에 해당한다. 이는 등록 트리거의 도달을 이미 위험으로 보는 보유자 수 산정(부품 D-01, 미만 유지)과 부등호를 달리하는 것으로서, 각 규정의 문언에 따른 차이이다.

## 4. 저술 지위 및 검토 요청

전술한 바와 같이 본 부품은 대응 walkthrough가 없어 제1부의 논증을 본 명세에서 저술하였다. 따라서 다음 사항에 관하여 법률 검토가 필요하다. 첫째, 공개시장 부재 자산에서 4주 평균 거래량 기준이 영에 수렴하여 1% 기준으로 귀착된다는 해석의 타당성. 둘째, Rule 144(a)(2)·(e)(3)의 합산 단위와 부품 D-01이 사용하는 §12(g) held of record 산정 단위의 이동(異同). 셋째, 본 부품이 활성화되는 계열자 판정의 경계 및 비계열자에 대한 비적용의 범위. 넷째, Form 144 제출 요건(Rule 144(h)) 및 매도 방법 요건(Rule 144(f))과의 관계에서 본 부품의 판정 범위를 물량에 한정하는 것의 적절성. 확정된 논증은 element walkthrough로 승격하여 본 명세의 원 출처로 삼는다.

## 5. 시스템 내 위치

| 주 Recipe | R2 (§4(a)(7)·Rule 144 Resale) 중 Rule 144 분기 |

| 실행 시점 | 거래 전 관문(pre-trade) + 거래 후 갱신(post-trade commit) |
| 활성 조건 | 매도인이 계열자로 판정된 경우에 한한다(A-06). 비계열자·§4(a)(7) 경로에서는 작동하지 아니한다. |
| 의존 부품 | A-06(계열자·합산 단위) · A-04(신원) · C-00(경로 선택) · Manifest(발행총량·시장 유무) |

시스템의 4-Layer 구조와 온·오프체인 경계 원칙은 `SPEC.md` 제1·2절에 의한다. 상태의 오프체인 위치는 부품 D-01과 동일한 근거에 따른다(제10절).

## 6. 인터페이스 계약

본 절의 시그니처·타입·호출 규약은 개발팀의 실현가능성 확정 이전의 제안이다. 본 부품은 실행이 두 시점으로 나뉘므로 두 개의 진입점을 가진다.

```
checkPre(seller: PersonGroupRef, asset: AssetRef, amount: uint, ctx: TxContext) -> Result
commit(seller: PersonGroupRef, asset: AssetRef, amount: uint, at: timestamp) -> void   // 멱등

Result = { passed: bool, reasonCode: ReasonCode }
```

| 항목 | 규약 |
|---|---|
| 호출 주체 | `RecipeRegistry`(R2 Rule 144 분기, 계열자인 경우) → `checkPre` · `Router`(체결 후) → `commit` |
| 호출 시점 | `checkPre`는 체결 직전, `commit`은 체결 확정 직후 |
| `PersonGroupRef` | 지갑·개인이 아니라 A-06·A-04가 해소한 (a)(2) 합산 단위 |
| 읽는 상태 | 직전 3개월 누적 매도량(Layer 5) · `Manifest.sharesOutstanding` · `Manifest.hasPublicMarket`·`avgWeeklyVolume` |
| 쓰는 상태 | `commit`만 누적 매도량에 이번 매도를 추가한다 |
| 온·오프체인 경계 | 온체인은 누적·비교를, 오프체인은 합산 단위의 식별·발행총량·거래량의 확인을 담당한다. |

## 7. 입력 필드

| 필드 | 유형 | 출처 | 의미 |
|---|---|---|---|
| `amount` | uint | 거래 | 이번 매도 수량 |
| `trailingSold` | uint (상태) | Layer 5 | 직전 3개월간 합산 단위의 누적 매도량 |
| `manifest.sharesOutstanding` | uint | Manifest | 발행총량(1% 기준의 모수) |
| `manifest.hasPublicMarket` | bool | Manifest | 공개 거래시장 존재 여부 |
| `manifest.avgWeeklyVolume` | uint (선택) | Manifest / 시장 데이터 | 직전 4주 평균 주간 거래량(시장이 있는 경우) |
| `seller.isAffiliate` | bool | A-06 | 계열자 여부(활성 조건) |
| `seller.groupId` | id | A-06 / A-04 | (a)(2) 합산 단위 식별 |

## 8. 기능 요구사항

- **REQ-C08-1 (활성 조건).** 시스템은 매도인이 계열자로 판정된 경우에 한하여 본 부품을 적용하여야 한다. 비계열자의 매도에는 물량 한도를 적용하지 아니한다.
- **REQ-C08-2 (한도 산정).** 시스템은 한도를 `max(발행총량의 1%, 직전 4주 평균 주간 거래량)`으로 산정하여야 한다. 다만 `hasPublicMarket`이 거짓인 경우 거래량 기준을 영으로 보아 한도를 발행총량의 1%로 산정한다.
- **REQ-C08-3 (누적 판정).** 시스템은 직전 3개월간 합산 단위의 누적 매도량에 이번 매도량을 더한 값이 한도를 초과하는 경우 거래를 거절하여야 한다. 상한에 정확히 도달하는 매도는 허용한다.
- **REQ-C08-4 (합산 단위).** 시스템은 누적을 지갑이나 개인이 아니라 (a)(2) 합산 단위(`groupId`)를 키로 하여 관리하여야 한다.
- **REQ-C08-5 (상태 갱신).** 시스템은 거래가 체결된 경우에만 해당 매도량을 누적에 추가하여야 하며, 동일 `(txId, asset)`에 대한 갱신은 멱등이어야 한다.
- **REQ-C08-6 (이동창).** 시스템은 거래 시점으로부터 3개월이 경과한 과거의 매도를 누적에서 제외하여야 한다.

참고 의사코드:

```
function checkPre(seller, asset, amount):
    if not seller.isAffiliate: return { passed: true, reasonCode: PASS }   // 비계열자 비적용
    onePct = asset.manifest.sharesOutstanding / 100
    cap    = asset.manifest.hasPublicMarket
             ? max(onePct, asset.manifest.avgWeeklyVolume)
             : onePct
    sold   = TrailingSold[asset][seller.groupId]     // 직전 3개월 누적(이동창)
    if sold + amount > cap:
        return { passed: false, reasonCode: FAIL_VOLUME_LIMIT_EXCEEDED }
    return { passed: true, reasonCode: PASS }

function commit(seller, asset, amount, at):
    if seller.isAffiliate:
        TrailingSold[asset][seller.groupId].add(amount, at)   // 3개월 경과분은 만료
```

## 9. reasonCode

| Code | 발생 조건 | 처리 |
|---|---|---|
| `FAIL_VOLUME_LIMIT_EXCEEDED` | 누적 + 이번 매도가 한도 초과 | 거절. 프런트엔드는 잔여 한도와 다음 창 개시 시점을 안내한다. |
| `REVIEW_AGGREGATION_UNCERTAIN` | (a)(2) 합산 단위가 불명확 | 심사 회부. A-06·A-04 확인 후 재판정. |
| `PASS` | 비계열자이거나 한도 내 | 통과. commit에서 누적 갱신. |

## 10. 상태 요구사항

- **REQ-C08-7 (상태 위치·권위).** 누적 매도량은 off-chain 컴플라이언스 데이터 레이어(Layer 5)에 유지한다. 상태 키가 (a)(2) 합산 단위이고 크로스-venue 합산을 요하기 때문이다. 누적의 권위 있는 원천은 Trusted Issuer(Securitize)의 attestation anchor이며, 체인 전반의 감시는 탐지 목적일 뿐 본 누적의 권위 원천이 아니다(`SPEC.md` 제6.4절).
- **REQ-C08-8 (원자성).** `checkPre`와 `commit` 간의 누적 접근은 원자적이어야 하며, 동시적 매도가 한도를 초과하도록 허용하여서는 아니 된다.
- **REQ-C08-9 (이동창 구현).** 누적은 3개월 이동창으로 구현하여야 하며, 개별 매도는 그 일자와 함께 기록하여 3개월 경과 시 자동으로 만료되도록 한다.

## 11. 불변식

1. `TrailingSold[asset][groupId]`는 직전 3개월간 체결된 매도량의 합과 같다. 거절된 시도는 포함하지 아니한다.
2. 한도는 공개시장이 있는 경우 `max(1%, 4주 평균 거래량)`, 없는 경우 발행총량의 1%이다.
3. 상한에 도달한 매도는 적법하며, 이를 초과하는 매도만이 거절된다.
4. 본 부품은 계열자의 매도에 한하여 작동한다.
5. `commit`은 멱등이다.

## 12. 의존성

```
A-06(계열자·control) → isAffiliate·groupId → C-08 (활성 조건·합산 단위)
A-04(신원)           → 합산 단위 해소 → C-08
C-00(경로 선택)      → Rule 144 경로 선택 시에만 → C-08
Manifest             → 발행총량·시장 유무·거래량 → C-08
Layer 5              → 누적 상태·권위(TA attestation anchor) → C-08
```

본 부품은 보유기간(C-01)·매도 방법(Rule 144(f))·Form 144(Rule 144(h))와 함께 계열자의 Rule 144 재매각 조건을 구성하되, 그중 물량에 한한다.

## 14. Demo 및 Production 범위

| 구분 | Demo (Gasok) | Production |
|---|---|---|
| 활성 | §4(a)(7) 주 경로·비계열자 위주라 대체로 비활성 | 계열자의 Rule 144 경로에서 활성 |
| 상태 | 불요 또는 단순 mock | Layer 5 이동창 + TA attestation anchor |
| 합산 | 단순 personId | (a)(2) 합산 단위 |

§4(a)(7)이 주 경로이고 본 부품은 계열자의 Rule 144 경로에서만 작동하므로, 데모 단계에서는 대체로 비활성이며 mock으로 충분하다(ADR-008 D-B). Production에서 계열자 Rule 144 경로를 지원할 때 이동창 누적과 합산 단위 관리가 필요하다.

2. (a)(2) 합산 단위와 D-01의 §12(g) held of record 단위의 이동(제3.5절·D-01).

5. 이동창·원자성 구현 방식 — 개발팀 설계.
6. 부품 목록(Element Pool) 신규 등재 절차(ADR-004 freeze 변경).
